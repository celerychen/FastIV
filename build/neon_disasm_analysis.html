结论速览

手写的 fiv_cs_gray_16px_neon 比编译器自动向量化的标量 fiv_cs_to_gray_scalar_core 慢约 1.8×，但比纯标量（禁用向量化）快约 3×。 根因是 编译器生成的自动向量化代码本质上和手写 NEON 是同一套算法，而且它做得更好——用更宽的 16-bit lane、把右移融合进窄化指令、单次循环处理 48 像素。

反汇编证据：两段关键循环

用 clang -O2 -S 编译 src/image/fiv_image_color_space.c，定位两个函数的热循环：

  • 编译器自动向量化 来自 fiv_cs_to_gray_scalar → 标量 core 被 clang 自动向量化成 NEON（符号 LBB0_12）
  • 手写 NEON 来自 fiv_cs_to_gray_simd 的 NEON 分支，fiv_cs_gray_16px_neon 被内联（符号 LBB2_6）

① 编译器自动向量化（LBB0_12，16 像素主循环体）

; 一次迭代用 3 条 ld3 连续处理 48 像素
ld3.16b  { v16, v17, v18 }, [x27], #48
ld3.16b  { v19, v20, v21 }, [x28], #48
ld3.16b  { v22, v23, v24 }, [x30], #48
umull.8h   v6, v19, v1        ; u16 += g * wg   (16-bit lane, 一次 8 像素)
umull2.8h  v7, v19, v4
umlal2.8h  v7, v16, v3        ; += r * wr
umlal.8h   v6, v16, v0
umull2.8h  v16, v22, v5
umull.8h   v17, v22, v2
addhn.8b   v6, v6, v17        ; ★ 加宽+右移+窄化 一步到位 (>>8 免费)
addhn2.16b v6, v7, v16
str        q6, [x26], #16     ; 一次存 16 字节灰度

② 手写 NEON（LBB2_6，单个 16 像素 quarter 体，循环内展开 3 次）

ld3.16b  { v18, v19, v20 }, [x5]      ; 只取 16 像素
ushll.8h   v21, v18, #0        ; widen (6 条，全显式)
ushll.8h   v22, v19, #0
ushll.8h   v23, v20, #0
ushll2.8h  v24, v18, #0
ushll2.8h  v25, v19, #0
ushll2.8h  v18, v20, #0
umull.4s   v19, v22, v16       ; u32 += g * wg  (32-bit lane, 只能 4 像素!)
umlal.4s   v19, v21, v0[0]
umlal.4s   v19, v23, v1[0]
xtn.4h     v19, v19            ; 先窄化到 16-bit
ushr.4h    v19, v19, #8        ; ★ 再显式右移 (独立指令!)
mov.d      v19[1], v20[0]      ; 重组 (额外搬运)
mov.d      v21[1], v18[0]
uzp1.16b   v18, v19, v21       ; 打包
str        q18, [x28]

手写版本里，同样的 16 像素被拆成 4 个 quarter（r0/r1/r2/r3），每个 quarter 都要一遍 xtn + ushr + mov + uzp1 重组。上面只是其中一个 quarter 的展开。

根因拆解（三条致命差异）

维度编译器自动向量化 (LBB0_12)手写 NEON (LBB2_6)代价
乘加 lane 宽度 umull.8h / umlal.8h
16-bit lane，一条指令覆盖 8 像素×3 通道		 umull.4s / umlal.4s
32-bit lane，一条只覆盖 4 像素，16 像素要拆 4 段		 指令数翻倍
右移 >>8 的实现 addhn.8b / addhn2.16b
加宽时直接丢弃高 8 位 = 零成本右移		 xtn + ushr #8 + mov + uzp1
窄化、移位、重组分三步，多一轮数据搬运		 额外 4 条/quarter
循环粒度 单次迭代 3×ld3 = 48 像素连续 每 16 像素一次 ld3 + 一大段重组 取数/存数开销占比更高

本质：手写内核因为用了 uint16x4 的四分之一拆分（vmlal_u16 的 32-bit 累加需要 4-lane），把本来一条 umull.8h 能干的活拆成了 4 份，而且没有利用 addhn 把 >>8 融合进窄化。编译器没有这些约束——它从标量源直接向量化，自然选了最宽的可用 lane 和最紧凑的 narrowing 指令。

为什么手写 NEON 依然比"纯标量"快 3×？

纯标量（-fno-vectorize）是逐字节 ldrb / mul / madd / lsr / strb（见 LBB0_17），每像素 ~5 条标量指令、无向量、无预取。手写 NEON 至少用 vld3 一次性解交织 16 像素、用向量乘加，所以仍有 3× 收益——只是这 3× 收益和编译器自动向量化的 5.6× 收益高度重叠，没有"增量"。

这意味着什么 / 该不该改？

  • 不是 bug：SIMD 路径 bit-exact 正确，且没有拖慢程序（仍比无向量化快）。
  • 收益已被编译器吃光：在 M4 / clang -O2 上，手写 NEON 是"重复造轮子"，既没更快，还多了一坨难维护的 intrinsic 代码。
  • 可选优化：若想让手写 NEON 真正赢，应改成编译器那套写法——vld3q_u8 + vmull_u16（16-bit lane）+ vaddhn_u16（融合 >>8），一次 16 像素、不拆 quarter。但即便如此，最多也只是和自动向量化打平，很难超越。
  • x86 路径另说：AVX2 在 x86 上通常能显著超越自动向量化（编译器对 deinterleave+shuffle 的识别不如手写 shuffle mask 精准），那一路仍有真实价值。

结论：ARM 侧可以保留手写 NEON 作为"显式可控"实现，但性能上不应期待它超越编译器；如果以性能为唯一目标，ARM 侧直接信任自动向量化、把精力放在 x86 AVX2 上更划算。
