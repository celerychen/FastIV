结论
1. v4 没打赢 v1，也没打赢 v3。 在 mat·vec 上 v4（共享+float4）≈ v2/v3（136–140 GF），明显落后于 v1 的 warp 级 float4（~162–165 GF）；在 matᵀ·vec 上 v4 反而最慢（9–145 GF）——因为它的“float4 叠加”只加速了共享内存里 x 的 tile 搬运，而真正的计算热点是按行跨 stride 读 A（无法 float4），且 64 活跃线程/块的写法降低了占用率。
2. cuBLAS 是天花板。 mat·vec 上 cuBLAS（~167 GF）与 v1 基本持平；matᵀ·vec 上 cuBLAS 在中小尺寸与“高瘦”形状（8192×1024）碾压所有手写版本（153 GF vs v3 的 60 / v4 的 22），只有在 8192² 这种大方阵手写版才逼近它。
3. 端到端瓶颈不在 kernel。 8192² 时 H2D 上传就要 ~39 ms，而 kernel 仅 ~0.8 ms（占端到端 95%+）。即便 kernel 追上 cuBLAS，端到端也几乎不变——必须靠 cudaMemcpyAsync + 多 stream 把传输与计算重叠（cudaGraph / 双缓冲）才能真正提速。
4. 对齐策略正确。 v4 仅在指针 16B 对齐且 stride 为 4 倍数时走 float4，否则退回 v3 标量等价——因此 1452 个含非对齐 stride 的用例全部通过，没有踩 v1 曾踩过的 misaligned-address 坑。

注：GFLOP/s = 2·rows·cols / kernel_time。复现见 test_matvet_cuda.cu + build_cuda.bat（已含 v4 与 cublas 源并链接 -lcublas）。
