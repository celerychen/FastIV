为什么 256×256 还差一点？

256² 的 GEMV 只有 0.13 MFLOP，理想计算本身只需约 4μs（35 GF 下）。但 每次 CUDA kernel launch 有 ~3–5μs 的固定开销。 我的任何手写路径都是 2 次 launch（主 kernel + 归约 kernel，或 memset + atomic），所以时间 ≈ 2×launch(6–7μs) + 计算(2μs) ≈ 8μs → 19 GF，直接卡死在 launch 开销上。

试过的两个方向都没破局：

  • 把列块 256→32 拉满占用率（64 block）→ 占用率翻 8 倍，但仍是 2 次 launch，时间纹丝不动（仍 ~17–19 GF）。
  • 单 kernel + atomicAdd 消除归约第二次 launch → 但必须先 cudaMemsetAsync 清零 dst 才能累加，launch 次数又补回 2 次；且 512² 每列被 16 个 row block 竞争 atomic 反而退化（60→42 GF，已通过阈值收紧修复）。

cuBLAS 用 CUDA Graph / 特化 kernel 把 launch 重叠或消除，才做到 ~4–5μs（24–35 GF）。这是 GPU 小矩阵 GEMV 的本质限制，不是算法写错。

本次交付

  • v5 新增 小矩阵单 kernel + atomicAdd 路径（mat_t_vec_v5_kernel_atomic），列块取 32 以拉高小矩阵占用率；阈值 rows·cols ≤ 256² 走此路径，其余走已验证的 2D 分块 + 部分积双 kernel。
  • 正确性 1694/1694 全绿（含非对齐 stride）。
  • 512×512 追平 cuBLAS（60 vs 59 GF）；256×256 差距收窄至约 1.3×。

要真正追平 256×256 的下一步

两条可行路线（均超出"改 v5"范围，需确认是否做）：

  • A. CUDA Graph 版（v6）：把 H2D + kernel + D2H 捕获成 graph，execute 几乎零 launch 开销，预期把 256² 从 ~19 GF 拉到接近 cuBLAS 的 24–35 GF。
  • B. 小矩阵直接 dispatch 到 cublasSgemm：把 vec 当 (rows×1) 矩阵，用 GEMM 式高占用 kernel 实现 GEMV，等于复用 cuBLAS 自身。
